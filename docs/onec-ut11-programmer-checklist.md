# Чеклист программиста 1С: HTTP-сервис Izibuy (УТ 11)

**Отдать вместе с:** [onec-http-contract.md](./onec-http-contract.md)  
**Контекст для заказчика:** [onec-ut11-setup-guide.md](./onec-ut11-setup-guide.md)

**Цель:** типовая **УТ 11**, HTTP JSON API. Сайт Izibuy ходит на ваши URL с `Authorization: Bearer <ключ>`.  
**Не цель v1:** выгрузка статусов заказа обратно на сайт; CommerceML; OData.

---

## 0. Входные данные (запросить у заказчика)

- [ ] База: типовая УТ 11.x (уточнить релиз, например 11.5)
- [ ] Клиент-сервер / облако: есть ли уже публикация на веб-сервере
- [ ] Какой **вид цены** отдавать на сайт (розничная / договор / конкретный тип цен)
- [ ] Какой **склад** (или все склады суммой) считать остатком `stock`
- [ ] Нужны ли в выгрузке только позиции с остатком > 0 или вся номенклатура с `isActive`
- [ ] Организация / контрагент «покупатель с сайта» по умолчанию для документа «Заказ покупателя»
- [ ] Согласованный **API-ключ** (строка, хранить в константе/регистре; тот же ключ в кабинете сайта)

---

## 1. Конфигурация: HTTP-сервис

- [ ] Создать HTTP-сервис, например `IzibuyExchange`
- [ ] Корневой URL-шаблон, например `izibuy`  
  Итоговый base (после публикации) вида:  
  `https://<host>/<publication>/hs/izibuy`  
  **Без** завершающего `/`. Сайт дописывает `/v1/...`
- [ ] Шаблоны URL:
  - [ ] `v1/health` — GET
  - [ ] `v1/nomenclature` — GET
  - [ ] `v1/customer-orders` — POST
- [ ] `Content-Type` ответов: `application/json; charset=utf-8`
- [ ] Во всех методах: проверка заголовка `Authorization`  
  - ожидается `Bearer <ключ>`  
  - иначе **401** + `{ "message": "Unauthorized" }` (или аналог)

---

## 2. `GET /v1/health`

- [ ] Без тяжёлой логики
- [ ] **200** + тело минимум: `{ "ok": true }`
- [ ] Проходит с валидным Bearer; без ключа — 401

**Критерий приёмки:** Postman/curl с ключом → 200 JSON.

---

## 3. `GET /v1/nomenclature`

### Данные

- [ ] Источник: справочник **Номенклатура** (или согласованный отбор)
- [ ] `guid` — **стабильный** идентификатор (рекомендуется UUID/уникальный идентификатор ссылки номенклатуры как строка). Не менять между вызовами
- [ ] `name` — наименование для витрины
- [ ] `article` — артикул (если есть), иначе `""` или не передавать
- [ ] `price` — число ≥ 0 по согласованному виду цены (одна валюта, рубли)
- [ ] `stock` — целое ≥ 0, свободный остаток по согласованному складу (сайт сам режет до 9999)
- [ ] `isActive` — `false` для снятых с продажи / помеченных на удаление / запрещённых к продаже
- [ ] `description` — опционально (строка)
- [ ] `imageUrls` — опционально (массив URL); в v1 можно `[]`

### Ответ

- [ ] Обёртка строго: `{ "items": [ ... ] }`
- [ ] Позиции без `guid` / `name` / валидной `price` **не отдавать** (сайт их отбросит)
- [ ] Пустой список допустим: `{ "items": [] }`

### Производительность (минимум)

- [ ] Не отдавать «тяжёлые» вложения без нужды
- [ ] При тысячах позиций — согласовать пагинацию **позже**; в v1 допустим полный список, если укладывается в таймаут ~30 с

**Критерий приёмки:** ответ валидный JSON; у 2–3 тестовых позиций совпадают цена/остаток с тем, что видно в УТ.

---

## 4. `POST /v1/customer-orders`

### Назначение в УТ

- [ ] Создавать документ **«Заказ покупателя»** (не реализацию, не черновик «на листочке» вне документов — именно проводимый/записываемый заказ по правилам учёта заказчика)

### Вход (JSON)

Поля контракта: `externalId`, `orderId`, `createdAt`, `fulfillmentMethod` (`pickup`|`delivery`), `deliveryAddress`, `deliveryAddressFlat`, `items[]` (`guid`, `article`, `name`, `quantity`, `price`), `totalAmount`.

- [ ] Парсинг JSON тела запроса
- [ ] Поиск номенклатуры **по `items[].guid`** (тот же идентификатор, что в `/nomenclature`)
- [ ] Если guid не найден — **4xx** + `{ "message": "..." }` (понятный текст), документ не создавать
- [ ] Количество и цена из запроса сайта (цена на момент заказа уже зафиксирована сайтом)

### Идемпотентность (обязательно)

- [ ] Ключ идемпотентности: поле **`externalId`** (строка вида `<orderId>:<sellerId>`)
- [ ] Повторный POST с тем же `externalId`:
  - [ ] **не** создаёт второй заказ
  - [ ] возвращает **200/201** и тот же идентификатор документа 1С в ответе

Рекомендация: хранить соответствие `externalId` → ссылка на документ (регистр сведений / доп. реквизит).

### Ответ

- [ ] **200 или 201** + `{ "externalId": "<номер или GUID документа в 1С>" }`  
  Здесь `externalId` в ответе — **ваш** id документа (не путать с входным `externalId` запроса; сайт сохранит строку ответа как внешний id)

### Заполнение документа (уточнить с заказчиком)

- [ ] Организация
- [ ] Контрагент / партнёр (покупатель «с сайта» или создание по правилам)
- [ ] Соглашение / договор / вид цены — если требуются типовой УТ
- [ ] Склад
- [ ] Комментарий: можно писать `orderId` сайта + адрес (`deliveryAddress`)
- [ ] `fulfillmentMethod`: в комментарии или доп. поле (самовывоз / доставка)

**Критерий приёмки:** два одинаковых POST с одним `externalId` → один документ в списке заказов покупателей; в ответе стабильный id.

## 5. Публикация и сеть

- [ ] Опубликовать базу на веб-сервере (IIS/Apache по стандарту хостинга)
- [ ] В публикации включены **HTTP-сервисы**
- [ ] HTTPS предпочтительно (для боя)
- [ ] URL доступен:
  - [ ] с ПК заказчика (локальный тест)
  - [ ] с сервера сайта Izibuy (бой) — иначе VPN/белый список/туннель
- [ ] Firewall / антивирус не режут путь `/hs/...`

**Критерий приёмки:** с внешней машины:

```http
GET {baseUrl}/v1/health
Authorization: Bearer {apiKey}
```

→ 200 `{ "ok": true }`

## 6. Сдача заказчику (что передать)

- [ ] Итоговый **base URL** (без `/v1/...` на конце)
- [ ] **API-ключ** (не в общий чат; в кабинет сайта / менеджеру)
- [ ] Кратко: какой вид цены и какой склад в `stock`
- [ ] Скрин/пример ответа `/v1/nomenclature` (1–2 позиции)
- [ ] Скрин созданного «Заказа покупателя» после тестового POST

Заказчик вставляет URL+ключ в **Профиль → 1С** на сайте → «Проверить соединение» → «Обменять сейчас».

## 7. Тест-кейсы (прогнать до сдачи)

| # | Действие | Ожидание |
| --- | --- | --- |
| T1 | GET health без Authorization | 401 |
| T2 | GET health с ключом | 200 `{ "ok": true }` |
| T3 | GET nomenclature | `{ "items": [ ... ] }`, guid/name/price/stock ок |
| T4 | POST customer-orders валидный | 200/201, документ в УТ |
| T5 | Повтор T4 с тем же `externalId` | второй документ **не** создан |
| T6 | POST с несуществующим `guid` | 4xx + `message`, без документа |
| T7 | Неверный ключ на любом методе | 401 |

Эталон поведения сайта (mock): в репозитории `server` → `npm run onec:mock` (пути те же `/v1/...`).

---

## Вне scope (не делать в этой задаче)

- Статусы заказа УТ → сайт
- Обновление остатков по webhook (достаточно ответа на GET по cron сайта ~5 мин)
- Загрузка картинок из файлового хранилища 1С, если нет публичных URL
- Поддержка нескольких организаций/многофирменности без явного ТЗ

---

## Оценка (ориентир)

Для типовой УТ 11 с уже существующей публикацией веб: обычно **от нескольких часов до 1–2 дней**, если понятны вид цены/склад/контрагент.  
Если публикации HTTP ещё нет на облаке — заложить время на хостера/права публикации.
