# Микросервисы: что, когда и как выделять

> **TL;DR — сейчас НЕ выделять.** Проект — модульный монолит с сервисным слоем,
> фоновым воркером и очередями. Для текущего масштаба это **правильно**.
> Микросервисы добавляют сеть, распределённые транзакции, операционную сложность
> и **замедляют разработку** — их вводят, когда монолит становится узким местом
> (деплой, изоляция отказов, независимое масштабирование команд), а не «на вырост».
> Этот документ — карта на будущее и защита от преждевременного распила.

Согласовано с [`ROADMAP-SCALING.md`](ROADMAP-SCALING.md) (фаза 3, «Не делать рано»)
и [`../server/docs/HORIZONTAL-SCALING.md`](../server/docs/HORIZONTAL-SCALING.md).

## 1. Что у нас сейчас (и почему это уже «почти микросервис-ready»)

```
client / mobile ──► API-монолит (Express)
                       ├─ routes → controllers → services/ (доменный слой)
                       ├─ models (Mongoose) ─────────────┐
                       └─ queues/ (BullMQ) ──► Redis ──► worker.js (отдельный процесс)
                                                            └─ jobs/ (cron + consumers)
                                        общая MongoDB ◄──────┘
```

Ключевые «швы», по которым **можно** резать в будущем, уже существуют:

| Шов | Где | Почему это шов |
| --- | --- | --- |
| **Сервисный слой** | `server/services/<домен>/` | Логика уже сгруппирована по доменам (order, installment, raffle, loyalty, intro-ad, upload…). Границы будущих сервисов ≈ эти папки. |
| **Очередь задач** | `server/queues/`, `worker.js` | Асинхронная граница уже есть. Всё, что идёт через BullMQ, можно вынести в отдельный consumer-сервис **без изменения вызывающего кода**. |
| **API-контракт** | `contract/` (Zod) | Contract-first — при выносе сервиса контракт становится сетевым API, схемы переиспользуются. |
| **Разделение чтения** | `MONGO_URI_READ`, `mongoReadConnection.js` | Масштабирование чтения без выделения сервиса. |

Вывод: **сначала выжимаем монолит** (реплики API + read replica + Redis-кэш +
воркер) — это закрывает 95% проблем масштаба без микросервисов.

## 2. Когда выделять (триггеры, не догадки)

Выделяй сервис, только если видишь **конкретную боль**, которую монолит не решает:

| Триггер (что наблюдаешь) | Кандидат на вынос |
| --- | --- |
| Тяжёлые фоновые задачи (рассылки, обработка медиа, отчёты) съедают ресурсы и мешают API | **worker/notifications** — вынести consumer'ы |
| Нужно независимо масштабировать/деплоить поиск, лимиты Atlas Search | **search-service** |
| Медиа-нагрузка (загрузка/трансформация картинок) не вписывается в API | **media-service** |
| Разные части системы деплоятся разными командами и мешают друг другу | доменные сервисы (order, installment) |
| Отказ одного домена (напр. розыгрыши) роняет весь API | изоляция отказов → вынос домена |
| Нужен другой стек/язык для части (ML-антифрод, аналитика) | отдельный сервис на своём стеке |

Если ни один триггер не горит — **не режь**. «На будущее» здесь = плати сложностью
сейчас за пользу, которой пока нет.

## 3. Что выделять первым (по возрастанию риска)

Порядок = «легче вынести и меньше связность» → «сложнее и связнее».

### 🥇 1. Notifications / e-mail worker — самый лёгкий
- **Почему первый:** уже за очередью (`enqueueSendEmailVerification`, BullMQ). Вызывающий
  код кладёт задачу в Redis — ему всё равно, кто её обработает.
- **Как:** взять `worker.js` + `jobs/` + relevant `services/` (email, уведомления),
  собрать как отдельный деплой-юнит, слушающий тот же Redis. API не меняется.
- **Данные:** читает ту же Mongo (пока) — это ок для consumer'а.
- **Риск:** низкий. Фактически это «worker как отдельный сервис», а он уже почти такой.

### 🥈 2. Media / upload service
- **Почему:** загрузка/отдача/трансформация картинок — I/O-bound, хорошо изолируется,
  уже развязано через S3/CDN и `services/upload/`.
- **Как:** вынести `POST /upload*` + `GET /upload/private/*` + S3-логику. API проксирует
  или клиент ходит напрямую (signed URL).
- **Данные:** свои (бакеты S3), почти не пересекается с основной БД.
- **Риск:** средний (нужно аккуратно с приватными файлами — см. `deploy/PROD-S3-CDN.md`).

### 🥉 3. Search service
- **Почему:** каталожный поиск (Atlas Search) — независимый профиль нагрузки/масштаба.
- **Как:** сервис индексирует товары (подписка на события изменения товара через очередь)
  и отдаёт поиск. API дергает его по HTTP.
- **Данные:** свой индекс (OpenSearch/Elasticsearch) — денормализованная копия.
- **Риск:** средний-высокий (нужна синхронизация индекса, eventual consistency).

### 4. Доменные сервисы (order / installment / raffle) — последними
- **Почему последними:** здесь **деньги, транзакции и связность**. Заказы завязаны на
  товары, остатки, баллы лояльности, рассрочку. Вынос ломает ACID-транзакции
  (`runInTransaction`), которые сейчас держат инварианты (напр. фикс гонки оверселла).
- **Как (если реально придётся):** saga/оркестрация вместо распределённых транзакций,
  outbox-паттерн для событий, компенсирующие операции. Это **большой** проект.
- **Риск:** высокий. Не трогать, пока нет сильной организационной причины.

## 4. Как выделять (паттерн, а не «переписать с нуля»)

**Strangler Fig** — душим монолит по частям, не останавливая систему:

1. **Найди границу** = папка в `services/`. Убедись, что домен общается с остальными
   через **явные вызовы функций**, а не лазит в чужие модели напрямую.
2. **Контракт-first.** Опиши API будущего сервиса в `contract/` (Zod). Пока это
   in-process вызов, но с формальной схемой.
3. **Разорви прямой доступ к данным.** Сервис-кандидат должен ходить в БД **только
   через свой слой**. Другие домены — только через его API/события, не через его модели.
4. **Асинхронность через очередь.** Всё, что можно сделать событием (уведомить,
   переиндексировать, начислить), — через BullMQ. Это будущий сетевой шов «бесплатно».
5. **Вынеси процесс, оставь код.** Собери домен как отдельный деплой-юнит из **того же
   монорепо** (не отдельный репозиторий сразу). Общий `contract/`, `packages/`.
6. **Своя БД — в последнюю очередь.** Сначала отдельный процесс на **той же** Mongo
   (проще). Отдельная БД — только когда нужна независимость масштаба/отказа; тогда
   синхронизация через события (outbox) и eventual consistency.
7. **Наблюдаемость до выноса.** Трейсинг (`requestId` уже есть), метрики per-domain,
   алерты. Без этого распределённую систему не отладить.

**Монорепо остаётся.** Микросервисы ≠ мультирепо. `contract/` и `packages/*` — общий код.

## 5. Анти-паттерны (чего НЕ делать)

- ❌ **Распил «на вырост»** без горящего триггера из §2.
- ❌ **Распределённые транзакции** между order/installment/loyalty вместо ACID —
  пока помещается в один монолит, это подарок, а не долг.
- ❌ **Микросервис на один эндпоинт** («наносервисы») — оверхед > польза.
- ❌ **Общая БД, в которую лазят все сервисы** — это «распределённый монолит»,
  худшее из двух миров. Либо один процесс + одна БД, либо сервис + своя БД.
- ❌ **Отдельные репозитории на старте** — теряешь атомарные изменения контракта.
- ❌ **k8s/service mesh раньше 2-го сервиса** — сложность без выгоды.

## 6. Конкретный первый шаг (когда решишь начать)

Самый безопасный «нулевой» вынос — **сделать worker полноценным отдельным сервисом**
(он уже отдельный процесс, шаг маленький):

1. Отдельный systemd/PM2/контейнер-юнит `izibuy-worker` → `npm run start:worker`
   (уже поддержано; `worker.js` ставит `CRON_LEADER=true`).
2. `REDIS_URL` на API и воркере → задачи идут через BullMQ (`isBullMqEnabled`).
3. API на `CRON_LEADER=false` (или не задавать — в prod default «не запускать cron»,
   при этом [`index.js`](../server/index.js) теперь **предупреждает**, если cron нигде не идёт).
4. Мониторить очередь (глубина, fail rate) — это и есть твой первый «межсервисный» SLO.

Это даёт изоляцию фоновой нагрузки от API **без** распределённых транзакций и без
своей БД — 80% пользы за 5% сложности. Дальше — только по триггерам §2.

## 7. Итоговая рекомендация

| Вопрос | Ответ |
| --- | --- |
| Нужны ли микросервисы **сейчас**? | **Нет.** |
| Готов ли код к ним архитектурно? | Да — сервисный слой, очереди, контракт, worker уже есть. |
| Что делать вместо этого? | Выжать монолит: реплики API + read replica + Redis-кэш + отдельный worker (фаза 2 роадмапа). |
| Первый реальный кандидат? | Worker/notifications (уже за очередью). |
| Когда начинать? | Когда загорится конкретный триггер из §2, не раньше. |
