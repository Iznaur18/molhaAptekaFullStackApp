# ЛОБО — курьерская служба (DMS Wayset)

Локальная служба доставки по Чеченской Республике. Первый живой перевозчик в
каркасе `services/shipping`; СДЭК, Яндекс и Почта остаются заглушками.

## Что решено (02.09.2026)

| Вопрос                        | Решение                                                       |
| ----------------------------- | ------------------------------------------------------------- |
| Чей аккаунт в ЛОБО            | Один на платформу, ключи в `server/.env`                      |
| Кто платит за доставку        | Покупатель курьеру при получении (`is_paid: false`)           |
| Когда заказ уходит в службу   | Когда продавец собрал — переход в `ready_to_ship`             |
| Где показывается              | Только пользователям Чечни (`RU-CE`)                          |

## Ключи

Без любого из трёх служба считается **ненастроенной**: наружу не предлагается,
товар с ней создать нельзя, в сеть клиент не ходит вовсе.

```bash
LOBO_API_KEY=ws_...
LOBO_API_LOGIN=...
LOBO_API_PASSWORD=...
# Необязательно, по умолчанию боевой Wayset:
LOBO_API_BASE_URL=https://services.wayset.ru/api/v1/external
```

Ключ выпускается в кабинете Wayset: заведение Gitorg → «Настройки» →
«Подключения» → «API-ключи». У ключа есть срок действия. Шаблон — в
`.env.example`.

## API службы

База `https://services.wayset.ru/api/v1/external`, описание — `GET /docs`.
Авторизация **двумя** заголовками сразу: `X-API-Key` и
`Authorization: Basic base64(логин:пароль)`.

| Метод  | Путь                  | Зачем нам                                        |
| ------ | --------------------- | ------------------------------------------------ |
| `GET`  | `/ping`               | Проверить ключ                                   |
| `POST` | `/estimate`           | Цена (`total`) и `quote_token` на 5 минут        |
| `POST` | `/orders`             | Создать заказ; идемпотентно по `external_id`     |
| `GET`  | `/orders`             | Найти заказ по нашему номеру, если id потерялся  |
| `GET`  | `/orders/{id}`        | Прочитать статус                                 |
| `POST` | `/orders/{id}/track`  | Ссылка отслеживания для покупателя               |
| `POST` | `/orders/{id}/cancel` | Отменить до забора груза                         |

**Вебхуков у службы нет** — статусы опрашиваем сами. Лимит 60 запросов в
минуту на IP: за проход крон берёт не больше 20 отправлений.

Наш номер заказа — `<orderId>:<sellerId>`, уходит в `external_id`. Статус и
отмена у Wayset идут по **их** `id`: храним его в
`shipments[].shippingCarrierOrderId`. Если он не записался, ищем заказ по
нашему номеру в `GET /orders`.

Заказ уходит с `tariff: "car"` (легковой, до 20 кг), `payment_method: "cash"`
и `is_paid: false` — покупатель платит курьеру. Перед созданием берём свежий
расчёт: его `quote_token` закрепляет цену. Своей цены мы не передаём.

## Как проходит заказ

1. Продавец из Чечни выбирает **ЛОБО** в «Выберите способ доставки» на товаре.
2. Покупатель видит службу на чекауте и **примерную** цену через `/estimate`.
   Точную назовёт курьер — так и написано в интерфейсе.
3. Продавец доводит отправление до «Готов к отгрузке» → заказ уходит в DMS.
4. Крон раз в 3 минуты опрашивает статусы и двигает нашу лестницу.
5. Курьер привозит, покупатель платит ему и **подтверждает получение сам**.

### Раскладка статусов

| Статус ЛОБО                         | Наша ступень   | Почему                                        |
| ----------------------------------- | -------------- | --------------------------------------------- |
| `draft`, `new`, `merged`, `assigned`, `accepted`, `arrived` | не двигаем | Товар ещё у продавца, покупателю сообщать нечего |
| `in_progress` («Забран»)            | `in_delivery`  | Курьер забрал — товар в пути                  |
| `done` («Доставлен»)                | `delivered`    | Привёз; сделку закрывает покупатель, не служба |
| `cancelled`                         | не двигаем     | Разбирается человеком                          |

Сделку по слову службы **не закрываем**. «Доставлен» проходит через штатный
`markOrderItemDeliveredBySeller` — на нём висят счётчик продаж и прочие
эффекты, терять их из-за чужого статуса нельзя.

## Где что лежит

| Файл                                              | Ответственность                        |
| ------------------------------------------------- | -------------------------------------- |
| `constants/loboConstants.js`                      | URL, таймауты, статусы, интервал опроса |
| `services/shipping/lobo/loboClient.js`            | HTTP: расчёт, создание, чтение, отмена |
| `services/shipping/lobo/loboProvider.js`          | Служба в общем реестре перевозчиков    |
| `services/shipping/lobo/loboShipmentOrders.js`    | Передача отправления и отмена          |
| `services/shipping/lobo/loboStatusSync.js`        | Опрос статусов и догон непереданных    |
| `services/shipping/estimateShipmentDelivery.js`   | Расчёт цены для чекаута                |
| `scripts/loboMockServer.mjs`                      | Мок DMS для отладки без ключей         |

Ручка расчёта — `POST /order/shipping-estimate`, внутри префикса `/order`
намеренно: новый префикс потребовал бы правки nginx на сервере, а конфиг
живёт отдельно от кода (см. `docs/deploy/nginx-api-prefixes.txt`).

## Отладка без ключей

```bash
cd server && npm run lobo:mock
```

Мок поднимается на `http://127.0.0.1:3092/api/v1/external`, ключи
`dms_mock_key` / `mock:mock`, статус сам едет по таймеру
(`LOBO_MOCK_STEP_SECONDS`, по умолчанию 20 секунд). Повторное создание с тем
же `external_id` возвращает существующий заказ — удобно отлаживать ретраи.

Тесты гоняются против него же: `loboClient`, `loboHandover`, `loboStatusSync`.

## Что может пойти не так

**Служба не ответила при передаче.** Ступень не откатывается: продавец свою
часть сделал. Отправление подберёт крон (`retryPendingLoboHandovers`), но
только пока оно в `ready_to_ship`.

**Курьер забрал и довёз между опросами.** Пропущенная ступень догоняется:
позиции проводятся через `in_delivery` и только потом в `delivered`. Без
этого отправление зависало в очереди навсегда.

**Нет координат.** Служба не примет заказ без широты и долготы — и точки
отправления, и адреса покупателя. Координаты доставки приходят с формы
(подсказка адреса или точка на карте) и лежат в `Order.deliveryAddressGeo`.
Стандартизация DaData отключена, полагаться на неё нельзя.

**Нет телефона продавца.** Служба звонит ему, поэтому проверяем до вызова —
иначе получили бы 400 уже после нажатия кнопки.

**429 от службы.** Читается как «недоступна», а не как ошибка нажавшего:
это наш перебор с частотой.

## Ограничение по региону

`SHIPPING_PROVIDER_REGIONS` в контракте: у ЛОБО `["RU-CE"]`, у остальных
`null` (вся страна). Регион неизвестен — локальную службу не предлагаем:
лучше не показать доступное, чем пообещать несуществующее.

Регион берётся с **точки отправления товара**, а не с прописки продавца:
курьер приедет именно туда.

## Не сделано

- Панель админа для включения и выключения служб. Сейчас доступность задана
  константами `SHIPPING_PROVIDER_ENABLED`; их надо переносить в базу.
  Важно: регион — ограничение **поверх** включённости, схлопывать их в один
  флаг нельзя, иначе включённая служба покажется всей стране.
- Статус ЛОБО и ссылка отслеживания пока нигде не показываются в интерфейсе.

## Проверено живьём (22.09.2026, тестовый ключ)

`/ping`, `/cities`, `/tariffs`, `/payment-methods`, `/estimate` (2,6 км по
Грозному = 260 ₽) и один **черновик** заказа (`draft: true`, id 224): создан,
прочитан, отменён — курьер не выезжал. Чего нет в документации:

- В заказе цена — `cost` / `final_cost`; `total` есть только в расчёте.
- `POST /orders/{id}/track` отвечает 400, пока курьер не на заказе: ссылка
  доступна в `accepted`, `arrived`, `in_progress`. Поэтому её берёт опрос, а
  не передача заказа.
- Поле `merged_into`: диспетчер может склеить заказ с другим в один рейс,
  статус нашего становится `merged` и дальше не движется. Опрос в этом случае
  читает заказ из `merged_into`.
- В заказе есть данные курьера: `courier_name`, `courier_phone`,
  `courier_car_brand/color/number`, `courier_eta_min`, координаты.
